2. Match Expression (replaces switch)

// switch - loose comparison, needs break, no return value
// match - strict comparison, no break needed, returns value

$result = match($status) {
    'active', 'published' => 'visible',
    'draft'               => 'hidden',
    'archived'            => 'removed',
    default               => throw new \InvalidArgumentException("Unknown: $status"),
};

3. Constructor Property Promotion

// Before

    private string $name;
    private string $email;

    public function __construct(string $name, string $email) {
        $this->name = $name;
        $this->email = $email;
    }
}

// PHP 8 - promoted
class User {
    public function __construct(
        private string $name,
        private string $email,
    ) {}
}

4. Enums (PHP 8.1)

enum Status: string {
    case Active = 'active';
    case Inactive = 'inactive';
    case Suspended = 'suspended';

    public function label(): string {
        return match($this) {
            self::Active    => 'Active User',
            self::Inactive  => 'Inactive User',
            self::Suspended => 'Account Suspended',

}

// Usage

== vs === (They WILL Ask This)

// == (loose) - type juggling, compares value after coercion
0 == 'foo'    // true in PHP 7, FALSE in PHP 8 (changed!)
0 == ''       // true in PHP 7, FALSE in PHP 8
0 == null     // true
'' == null    // true
1 == '1'      // true
1 == '1abc'   // true (PHP 7), true with deprecation notice

// === (strict) - compares value AND type, no coercion
0 === 'foo'   // false
0 === false   // false
1 === '1'     // false
null === ''   // false

// SENIOR ANSWER: Always use === in production code.
// Type juggling bugs are a common source of security vulnerabilities.
// PHP 8 fixed many of the worst == behaviors, but === is still safer.

Memory Management & Garbage Collection

Reference Counting: PHP uses reference counting as its primary memory management. Each variable has a refcount. When refcount hits 0, memory is freed immediately.

Circular Reference GC: The cycle collector handles circular references (e.g., parent->child->parent). It runs when a root buffer of 10,000 potential roots is full.

// Triggering GC manually
gc_collect_cycles();     // Force garbage collection
gc_enabled();            // Check if GC is enabled
gc_mem_caches();         // Free memory caches (PHP 8.1)

// Memory monitoring
memory_get_usage(true);  // Real memory allocated from OS
memory_get_peak_usage(); // Highest memory point in request

// Senior tip: Use weak references for caching to prevent memory leaks
$cache = new WeakMap();
$cache[$object] = computeExpensiveResult($object);
// When $object is garbage collected, the cache entry is too

SOLID Principles (Senior Must-Know)

S - Single Responsibility

// BAD - Controller does everything
class UserController {
    public function store(Request $request) {
        $user = User::create($request->all());           // persistence
        Mail::send(new WelcomeEmail($user));              // email
        Slack::notify("New user: {$user->name}");         // notification
        $user->subscription()->create(['plan' => 'free']);// billing
        return response()->json($user);
    }
}

// GOOD - Each class has one reason to change
class UserController {
    public function store(StoreUserRequest $request, CreateUserAction $action) {
        $user = $action->execute($request->validated());
        return new UserResource($user);
    }
}

class CreateUserAction {
    public function execute(array $data): User {
        $user = DB::transaction(fn() => User::create($data));
        event(new UserCreated($user)); // Listeners handle email, Slack, billing
        return $user;
    }
}

O - Open/Closed (Open for extension, closed for modification)

// BAD - Must modify class for each new payment method
class PaymentProcessor {
    public function process(string $type, float $amount) {
        if ($type === 'stripe') { ... }
        elseif ($type === 'paypal') { ... }
        elseif ($type === 'crypto') { ... } // Adding new types = modifying class
    }
}

// GOOD - Extend via new implementations
interface PaymentGateway {
    public function charge(float $amount): PaymentResult;
}

class StripeGateway implements PaymentGateway { ... }
class PayPalGateway implements PaymentGateway { ... }
class CryptoGateway implements PaymentGateway { ... } // Just add new class

class PaymentProcessor {
    public function process(PaymentGateway $gateway, float $amount): PaymentResult {
        return $gateway->charge($amount);
    }
}

L - Liskov Substitution

// BAD - Subclass changes behavior expectations
class Rectangle {
    public function setWidth(int $w): void { $this->width = $w; }
    public function setHeight(int $h): void { $this->height = $h; }
}

class Square extends Rectangle {
    public function setWidth(int $w): void {
        $this->width = $w;
        $this->height = $w; // Breaks LSP! Callers don't expect this
    }
}

// GOOD - Use composition or separate interfaces
interface Shape {
    public function area(): float;
}
class Rectangle implements Shape { ... }
class Square implements Shape { ... }

I - Interface Segregation

// BAD - Fat interface forces unnecessary implementations
interface Worker {
    public function code(): void;
    public function test(): void;

// GOOD - Segregated interfaces
interface Coder { public function code(): void; }

Key Design Patterns for Interview

Repository Pattern

interface UserRepositoryInterface {
    public function findById(int $id): ?User;
    public function findByEmail(string $email): ?User;
    public function paginate(int $perPage = 15): LengthAwarePaginator;
    public function create(array $data): User;
    public function update(User $user, array $data): User;
}

class EloquentUserRepository implements UserRepositoryInterface {
    public function __construct(private User $model) {}

    public function findById(int $id): ?User {
        return $this->model->find($id);
    }

    public function findByEmail(string $email): ?User {
        return $this->model->where('email', $email)->first();
    }

    public function paginate(int $perPage = 15): LengthAwarePaginator {
        return $this->model->latest()->paginate($perPage);
    }

    public function create(array $data): User {
        return $this->model->create($data);
    }

    public function update(User $user, array $data): User {
        $user->update($data);
        return $user->fresh();
    }
}

// Register in ServiceProvider
$this->app->bind(UserRepositoryInterface::class, EloquentUserRepository::class);

Strategy Pattern

interface ShippingCalculator {
    public function calculate(Order $order): Money;
}

class FlatRateShipping implements ShippingCalculator {
    public function calculate(Order $order): Money {
        return Money::of(9.99, 'USD');
    }
}

class WeightBasedShipping implements ShippingCalculator {
    public function calculate(Order $order): Money {
        return Money::of($order->totalWeight() * 0.50, 'USD');
    }
}

class FreeShipping implements ShippingCalculator {
    public function calculate(Order $order): Money {
        return Money::of(0, 'USD');

// Usage - strategy injected at runtime
class CheckoutService {
    public function calculateTotal(Order $order, ShippingCalculator $shipping): Money {
        return $order->subtotal()->plus($shipping->calculate($order));
    }
}

Performance Optimization (3+ Strategies Expected)

  1. OPcache: Caches compiled PHP bytecode. Eliminates parsing/compiling on every request. Enable in php.ini: opcache.enable=1
  2. JIT Compiler (PHP 8): Compiles bytecode to native machine code. Best for CPU-heavy operations, less impact on typical web apps.
  3. Database Query Optimization: Use eager loading (with()), proper indexes, avoid N+1 queries, use select() to limit columns.
  4. Caching: Redis/Memcached for query results, computed values, full-page cache. Laravel: Cache::remember()
  5. Queue Heavy Work: Offload emails, image processing, API calls to background jobs.
  6. PHP-FPM Tuning: Optimize worker count, process management (dynamic vs static), memory limits.
  7. Preloading (PHP 7.4+): Load commonly used classes at startup via opcache.preload.
  8. Profiling: Use Xdebug, Blackfire, or Laravel Telescope to find bottlenecks before optimizing.

PHP Under the Hood - How PHP Actually Works

Why this matters: Senior interviewers at Lemon-level platforms will ask "How does PHP actually process a request?" or "Why is PHP single-threaded and how does it still handle thousands of requests?" If you can explain this, you immediately separate yourself from mid-level candidates.

PHP is Single-Threaded - But That's a Feature

PHP runs a share-nothing architecture. Each request gets its own isolated process with its own memory. When the request ends, everything is destroyed. No shared state, no race conditions, no mutex locks.

This is why PHP "scales horizontally" so easily - just add more workers. Each worker is independent.

Request 1 ──> PHP Worker 1 (own memory, own variables, dies after response)
Request 2 ──> PHP Worker 2 (completely isolated from Worker 1)
Request 3 ──> PHP Worker 3 (no shared state between any workers)

// This is fundamentally different from Node.js (single process, event loop)
// or Java (threads sharing heap memory within one JVM)

PHP-FPM (FastCGI Process Manager)

PHP-FPM is the process manager that sits between Nginx and PHP. It maintains a pool of ready-to-go PHP worker processes so you don't pay the cost of starting a new process for every request.

Process Management Modes

ModeHow It WorksUse When
staticFixed number of workers, always runningPredictable traffic, dedicated servers. Best performance, highest memory.
dynamicMin idle workers kept warm, scales up to max on demandMost common. Good balance of performance and memory.
ondemandWorkers only spawned when request arrives, killed after idle timeoutLow-traffic sites, shared hosting. Saves memory, slower first request.
; /etc/php/8.3/fpm/pool.d/www.conf
[www]
pm = dynamic
pm.max_children = 50        ; Maximum worker processes
pm.start_servers = 10       ; Workers started on FPM boot
pm.min_spare_servers = 5    ; Keep at least 5 idle workers ready
pm.max_spare_servers = 15   ; Don't keep more than 15 idle
pm.max_requests = 500       ; Recycle worker after 500 requests (prevents memory leaks)
pm.process_idle_timeout = 10s

; SENIOR TIP: How to calculate max_children
; max_children = Available RAM / Average RAM per worker
; Example: 4GB available, each worker uses ~80MB
; max_children = 4096 / 80 = ~50 workers
; Monitor with: pm.status_path = /fpm-status

The Zend Engine is PHP's execution engine. It handles compilation and execution of PHP code.

OPcache - Why It's Critical

Without OPcache: Every request re-reads PHP files from disk, re-lexes, re-parses, re-compiles to opcodes. For Laravel with ~500+ files autoloaded per request, this is extremely wasteful.

With OPcache: Compiled opcodes are stored in shared memory. All workers read from the same cache. The lexer/parser/compiler step is completely skipped.

; php.ini - OPcache configuration
opcache.enable=1
opcache.memory_consumption=256        ; MB of shared memory for opcodes
opcache.interned_strings_buffer=16    ; MB for interned strings
opcache.max_accelerated_files=20000   ; Max cached files (Laravel needs ~4000+)
opcache.validate_timestamps=0         ; Production: DON'T check file changes (fastest)
                                      ; Development: set to 1 (checks every revalidate_freq)
opcache.revalidate_freq=0             ; Seconds between file change checks (if validate=1)

; SENIOR: In production, set validate_timestamps=0
; This means OPcache NEVER checks if files changed.
; After deployment, you must reset OPcache:
;   - php artisan opcache:clear (with a package)
;   - Kill PHP-FPM workers: systemctl reload php8.3-fpm
;   - Or use opcache_reset() in a deploy script

Preloading (PHP 7.4+)

; opcache.preload=/var/www/app/preload.php
; opcache.preload_user=www-data

// preload.php - loaded ONCE on FPM startup, stays in memory forever
// Classes loaded here are available to ALL requests without autoloading
require __DIR__ . '/vendor/autoload.php';

// Preload frequently used Laravel classes
$files = array_merge(
    glob(__DIR__ . '/app/Models/*.php'),
    glob(__DIR__ . '/app/Services/*.php'),
);
foreach ($files as $file) {
    opcache_compile_file($file);
}

// TRADE-OFF: Faster runtime, but FPM must be restarted on code changes.
// Best for production with stable code.

JIT Compiler (PHP 8.0+)

The JIT (Just-In-Time) compiler adds a layer ON TOP of OPcache. It takes frequently executed bytecode and compiles it directly to native machine code (x86/ARM assembly).

Without JIT:  PHP source → opcodes → Zend VM interprets each opcode
With JIT:     PHP source → opcodes → machine code → CPU executes directly

; php.ini
opcache.jit=1255              ; Enable JIT with tracing mode
opcache.jit_buffer_size=128M  ; Memory for compiled machine code

When JIT Helps vs Doesn't Help

Helps (CPU-bound)Doesn't Help (I/O-bound)
Math calculations, image processingDatabase queries (waiting for DB response)
Data transformation, loopsHTTP API calls (waiting for network)
Template renderingFile reads/writes (waiting for disk)
Cryptography, hashingMost typical Laravel web apps

Senior insight: Most Laravel apps are I/O-bound (waiting for database, Redis, external APIs). JIT gives maybe 5-10% improvement. OPcache alone gives 3-5x improvement. Focus on OPcache first, JIT is a bonus.

How Laravel Boots (The Request Lifecycle)

// public/index.php - EVERY request starts here

require __DIR__.'/../vendor/autoload.php';

// 2. Create the Application (Service Container)
$app = require_once __DIR__.'/../bootstrap/app.php';
// This creates the IoC container and registers base service providers

// 3. Create the HTTP Kernel
$kernel = $app->make(Illuminate\Contracts\Http\Kernel::class);

// 4. Handle the request through middleware pipeline
$response = $kernel->handle(
    $request = Illuminate\Http\Request::capture()
);

// INSIDE kernel->handle():
//   a) Bootstrap the application:
//      - Load .env file
//      - Load config files
//      - Register exception handler
//      - Register facades
//      - Register service providers (register() on ALL, then boot() on ALL)
//
//   b) Send request through global middleware stack:
//      TrustProxies → PreventRequestsDuringMaintenance →
//      ValidatePostSize → TrimStrings → ConvertEmptyStringsToNull
//
//   c) Router matches URL to route definition
//
//   d) Route middleware runs (auth, throttle, etc.)
//
//   e) Controller method executes
//
//   f) Response object built and returned

// 5. Send response to browser
$response->send();

// 6. Run terminable middleware (logging, session save)
$kernel->terminate($request, $response);

// 7. PHP-FPM worker cleans up ALL memory, returns to pool

Laravel Octane - Breaking the Share-Nothing Rule

Laravel Octane (with Swoole or FrankenPHP) keeps the Laravel application bootstrapped in memory across requests. Instead of booting Laravel fresh on every request:

Traditional PHP-FPM:
  Request 1: Boot Laravel (100ms) → Handle (50ms) → Destroy
  Request 2: Boot Laravel (100ms) → Handle (50ms) → Destroy
  Request 3: Boot Laravel (100ms) → Handle (50ms) → Destroy

Laravel Octane:
  Boot Laravel ONCE (100ms)
  Request 1: Handle (50ms) → Reset request state
  Request 2: Handle (50ms) → Reset request state
  Request 3: Handle (50ms) → Reset request state

Gotcha: Since the app stays in memory, you must be careful with static properties and singletons - they persist across requests. Use $this->app->scoped() instead of singleton() for request-scoped services.

class EnsureApiVersion
{
    public function handle(Request $request, Closure $next, string $version = 'v1'): Response
    {

            return response()->json(['error' => 'Unsupported API version'], 400);
        }

        // Before middleware logic
        $response = $next($request); // Pass to next middleware / controller
        // After middleware logic

        $response->headers->set('X-API-Version', $version);
        return $response;
    }
}

// Terminable middleware - runs AFTER response is sent to browser
class LogSlowRequests
{
    public function handle(Request $request, Closure $next): Response
    {
        $request->attributes->set('start_time', microtime(true));
        return $next($request);
    }

    public function terminate(Request $request, Response $response): void
    {
        $duration = microtime(true) - $request->attributes->get('start_time');
        if ($duration > 1.0) {
            Log::warning('Slow request', [
                'url' => $request->fullUrl(),
                'duration' => round($duration, 3),
            ]);
        }
    }
}

N+1 Problem & Eager Loading (Critical for Senior)

// THE N+1 PROBLEM
// BAD - 1 query for users + N queries for each user's posts
$users = User::all();
foreach ($users as $user) {
    echo $user->posts->count(); // Each iteration = 1 query!
}
// If 100 users = 101 queries!

// SOLUTION 1: Eager Loading with with()
$users = User::with('posts')->get();
// Only 2 queries: SELECT * FROM users; SELECT * FROM posts WHERE user_id IN (...)

// SOLUTION 2: Nested eager loading
$users = User::with(['posts.comments', 'profile', 'roles'])->get();

// SOLUTION 3: Constrained eager loading
$users = User::with(['posts' => function ($query) {
    $query->where('published', true)
          ->orderBy('created_at', 'desc')
          ->limit(5);
}])->get();

// SOLUTION 4: Lazy eager loading (after initial query)
$users = User::all();
$users->load('posts');

// SOLUTION 5: withCount for counting without loading
$users = User::withCount('posts')->get();
// $user->posts_count available, no posts loaded

// PREVENT N+1 globally in development
// AppServiceProvider::boot()
Model::preventLazyLoading(!app()->isProduction());

Queue System (When and How)

When to use queues: Any task that takes more than ~200ms and doesn't need an immediate response. Email sending, image processing, API calls to external services, report generation, search indexing. 
// Creating a Job
class ProcessPodcastUpload implements ShouldQueue
{
    use Queueable;

    public int $tries = 3;           // Retry up to 3 times
    public int $timeout = 120;       // Max 2 minutes
    public int $backoff = 30;        // Wait 30s between retries
    public int $maxExceptions = 2;   // Stop after 2 exceptions

    public function __construct(
        public readonly Podcast $podcast,
        public readonly string $filePath,
    ) {}

    public function handle(AudioProcessor $processor): void
    {
        $processed = $processor->transcode($this->filePath, 'mp3');
        $this->podcast->update([
            'processed_path' => $processed,
            'status' => 'ready',
        ]);
    }

    // Determine if the job should be retried
    public function failed(\Throwable $exception): void
    {
        Log::error('Podcast processing failed', [
            'podcast_id' => $this->podcast->id,
            'error' => $exception->getMessage(),
        ]);
        $this->podcast->update(['status' => 'failed']);
    }

    // Unique jobs - prevent duplicate processing
    public function uniqueId(): string
    {
        return $this->podcast->id;
    }
}

// Actions encapsulate a single business operation

class CreateOrderAction
{
    public function __construct(
        private OrderRepository $orders,
        private PaymentGateway $payment,
        private InventoryService $inventory,
    ) {}

    public function execute(User $user, array $items, string $paymentMethod): Order
    {
        return DB::transaction(function () use ($user, $items, $paymentMethod) {
            // 1. Validate inventory
            $this->inventory->assertAvailable($items);

            // 2. Create order
            $order = $this->orders->create([
                'user_id' => $user->id,
                'status' => OrderStatus::Pending,
                'total' => $this->calculateTotal($items),

            // 3. Attach items
            foreach ($items as $item) {
                $order->items()->create($item);
            }

            // 4. Process payment
            $this->payment->charge($order->total, $paymentMethod);
            $order->update(['status' => OrderStatus::Paid]);

            // 5. Fire event (listeners handle email, inventory decrement, etc.)
            event(new OrderPlaced($order));

            return $order;
        });
    }

    private function calculateTotal(array $items): int { ... }
}

The Middleware Pipeline - How It Actually Works

Laravel's middleware is the Chain of Responsibility pattern implemented via nested closures. Each middleware wraps the next one like Russian nesting dolls:

// What it LOOKS like:
$response = $middleware1->handle($request, function ($request) {
    return $middleware2->handle($request, function ($request) {
        return $middleware3->handle($request, function ($request) {
            return $controller->action($request);
        });
    });
});

// The Pipeline class builds this automatically:
// Illuminate\Pipeline\Pipeline

return (new Pipeline($this->app))
    ->send($request)
    ->through($this->middleware)    // Array of middleware classes
    ->then(function ($request) {    // The final destination
        return $this->router->dispatch($request);
    });

      │
      ▼

│                  │  │

│                  │  │

      ▼

Virtual DOM & Reconciliation (Interview Deep Dive)

How React Rendering Works:

  1. Trigger: State change, prop change, or parent re-render
  2. Render phase: React calls your component function, creating a new virtual DOM tree (React elements). This is pure - no side effects.
  3. Reconciliation: React diffs the new virtual DOM with the previous one using the "diffing algorithm" (O(n) heuristic):
    • Different element types? Tear down old tree, build new one
    • Same element type? Update only changed attributes
    • Lists? Use key prop to match elements across renders
  4. Commit phase: React applies the minimal set of actual DOM mutations. This is where useEffect runs.

React Fiber (React 16+):

Fiber is the reimplementation of React's core algorithm. It enables:

  • Incremental rendering - split rendering work into chunks
  • Prioritization - urgent updates (typing) over non-urgent (data fetch results)
  • Concurrency - pause, abort, or reuse work
  • Suspense & Transitions - built on Fiber's ability to pause rendering

React Fiber Architecture - Why It Exists

Problem (React 15 and earlier): Reconciliation was synchronous and recursive. A large component tree (e.g., 10,000 list items) would block the main thread for hundreds of milliseconds. The browser couldn't respond to user input, animations would stutter.

Solution (React 16+ Fiber): Rewrite reconciliation as an iterative, interruptible process using a linked list data structure called "Fiber."

// A Fiber node (simplified) - one per component/element
{
  type: UserProfile,           // Component function or HTML tag
  key: 'user-42',
  props: { userId: 42 },
  stateNode: DOM element,      // Actual DOM node (for host components)

  // Tree structure (linked list, not recursive tree)
  return: parentFiber,         // ← parent
  child: firstChildFiber,     // ← first child
  sibling: nextSiblingFiber,  // ← next sibling

  // Work tracking
  pendingProps: {},
  memoizedState: {},           // Hook states stored here
  effectTag: 'UPDATE',        // What DOM change is needed
  alternate: previousFiber,   // Points to current/work-in-progress pair
}

Virtual DOM vs Direct DOM

// Direct DOM manipulation:
element.style.color = 'red';     // Triggers style recalculation
element.style.fontSize = '16px'; // Triggers layout
element.style.margin = '10px';   // Triggers layout AGAIN
// Each change may trigger: Style → Layout → Paint → Composite
// 3 changes = potentially 3 layout passes (expensive!)

// React's Virtual DOM approach:
// 1. Batch all changes in memory (virtual DOM diff)
// 2. Calculate the MINIMAL set of actual DOM operations
// 3. Apply them in ONE batch
// Result: 3 changes = 1 layout pass

// SENIOR NUANCE: Virtual DOM is NOT faster than hand-optimized DOM.
// It's faster than NAIVE DOM manipulation.
// The real value is DEVELOPER EXPERIENCE:
// - Declarative code (describe WHAT, not HOW)
// - Automatic batching
// - Consistent mental model
// Frameworks like Svelte/Solid prove you CAN be fast without vDOM.

// composables/useFetch.js
import { ref, watchEffect } from 'vue';

export function useFetch(url) {
  const data = ref(null);
  const error = ref(null);
  const loading = ref(true);

  watchEffect(async (onCleanup) => {
    const controller = new AbortController();
    onCleanup(() => controller.abort());

    loading.value = true;
    error.value = null;

    try {
      const res = await fetch(url.value || url, { signal: controller.signal });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      data.value = await res.json();
    } catch (err) {
      if (err.name !== 'AbortError') error.value = err;
    } finally {
      loading.value = false;
    }
  });

  return { data, error, loading };
}

// composables/useDebounce.js
export function useDebounce(value, delay = 300) {
  const debounced = ref(value.value);
  let timer;

  watch(value, (newVal) => {
    clearTimeout(timer);
    timer = setTimeout(() => { debounced.value = newVal; }, delay);
  });

  return debounced;
}

SSR & Hydration

Nuxt 3 is the standard SSR framework for Vue 3 (like Next.js for React).

Hydration is the process of making server-rendered HTML interactive on the client:

  1. Server renders Vue components to HTML string
  2. HTML is sent to browser (fast First Contentful Paint)
  3. Browser loads Vue JS bundle
  4. Vue "hydrates" - attaches event listeners and makes components reactive
  5. App becomes fully interactive (Time to Interactive)

Hydration mismatch: When server HTML doesn't match what Vue would render on client. Common causes: browser-only APIs (window, localStorage), date/time formatting, random values. Fix with <ClientOnly> wrapper or onMounted for client-only logic.

Vue 3 Under the Hood - How Vue's Reactivity Works

Proxy-Based Reactivity System

Vue 3's reactivity is built on JavaScript Proxy (replacing Vue 2's Object.defineProperty). Understanding this is key to understanding why Vue behaves the way it does.

// What reactive() actually does (simplified):
function reactive(target) {
  return new Proxy(target, {
    get(target, key, receiver) {
      track(target, key);          // Register this property as a dependency
      const result = Reflect.get(target, key, receiver);
      if (isObject(result)) {
        return reactive(result);   // Deep reactivity - nested objects are also proxied
      }
      return result;
    },
    set(target, key, value, receiver) {
      const oldValue = target[key];
      const result = Reflect.set(target, key, value, receiver);
      if (oldValue !== value) {
        trigger(target, key);      // Notify all watchers of this property
      }
      return result;
    },
    deleteProperty(target, key) {
      const result = Reflect.deleteProperty(target, key);
      trigger(target, key);        // Vue 3 CAN detect property deletion!
      return result;               // (Vue 2 couldn't - needed Vue.delete())
    }
  });
}

Quiz PHP & Laravel - 15 Questions

Test your knowledge. These mirror Interview.io's question style and difficulty.

1. What does PHP 8's match expression return when no arm matches and there's no default?

Unlike switch (which silently falls through), match() throws an UnhandledMatchError if no arm matches. This is a deliberate design choice to prevent silent bugs.

2. In Laravel, what's the difference between $this->app->bind() and $this->app->singleton()?

bind() resolves a new instance every time it's requested from the container. singleton() resolves once and returns that same instance for all subsequent requests. Both are lazy (resolve on first request).

3. Which method prevents N+1 queries in Laravel?

with() is eager loading - it loads the relationship in a separate query using WHERE IN. This converts N+1 queries into just 2 queries regardless of how many users exist.

4. What is the purpose of Laravel's Service Container?

The Service Container (IoC Container) is the heart of Laravel. It manages class dependencies, resolves them automatically through dependency injection, and acts as a central registry for binding interfaces to implementations.

5. In PHP 8.1, what is a Fiber?

Fibers are stackful coroutines - they can be suspended and resumed. They enable cooperative (not preemptive) concurrency. They're the foundation for async frameworks like ReactPHP and Amp, but they're NOT threads (no parallelism).

6. When should you use a Gate vs a Policy in Laravel?

Gates are closures for simple, standalone authorization checks (e.g., "can manage users"). Policies are classes organized around a model with methods for each action (view, create, update, delete). Use Policies when authorization logic is tied to a specific Eloquent model.

7. What happens when you call Model::preventLazyLoading() in Laravel?

When enabled (typically only in non-production), accessing a relationship that wasn't eager loaded throws a LazyLoadingViolationException. This helps you catch N+1 query problems during development. Use Model::preventLazyLoading(!app()->isProduction()).

8. What is the correct order of method calls in a Laravel Service Provider?

Laravel calls register() on every service provider first (this is where you bind things into the container). Only after ALL providers are registered does it call boot() on each. This ensures all bindings are available during boot.

9. Which PHP function should you use for password hashing?

password_hash() is the only correct answer. It automatically generates a cryptographically secure salt. md5/sha256 are NOT suitable for passwords - they're fast hashing algorithms, making them vulnerable to brute force. Bcrypt/Argon2 are deliberately slow.

10. What does readonly mean on a PHP 8.2 class?

A readonly class in PHP 8.2 makes all declared properties implicitly readonly. Each property can only be initialized once (typically in the constructor) and cannot be modified afterward. It's perfect for DTOs and value objects.

11. How does Laravel's Queue system handle failed jobs by default?

After exhausting all retry attempts, Laravel stores the failed job in the failed_jobs database table. You can retry them with php artisan queue:retry. The job's failed() method is called if defined, allowing custom failure handling.

12. What is the purpose of DB::transaction()?

Database transactions ensure atomicity - either ALL queries within the transaction succeed, or ALL are rolled back. This is critical for operations like creating an order + decrementing stock, where partial completion would leave data inconsistent.

13. What's the difference between include and require in PHP?

include emits an E_WARNING if the file is not found (script continues). require emits an E_COMPILE_ERROR / fatal error (script stops). The _once variants prevent loading the same file twice. In modern Laravel, autoloading via Composer eliminates most direct usage.

14. When should you use Laravel Events vs Observers?

Events are explicit - you dispatch them deliberately for business-level actions (OrderPlaced, UserRegistered). Observers are implicit - they fire automatically on model lifecycle events (creating, created, updating, etc.). Observers are best for simple model concerns (generating UUIDs, clearing cache). Events are better for complex business logic because they're explicit and easier to trace.

15. What does php artisan route:cache do and when should you NOT use it?

Route caching serializes all route definitions into a single file for faster registration. It dramatically improves boot time for apps with many routes. However, closure-based routes cannot be serialized, so you must use controller-based routes. This is only for production - clear cache during development.

Quiz React - 10 Questions

1. What is the primary purpose of the key prop in React lists?

Keys help React's reconciliation algorithm efficiently determine the minimal set of DOM changes when a list updates. Without stable keys, React may re-render more elements than necessary or lose component state during reordering.

2. When does useEffect cleanup function run?

The cleanup function runs before the effect re-runs (when dependencies change) AND when the component unmounts. This ensures resources from the previous effect are cleaned up before the next effect sets up new ones.

3. What is React Fiber?

React Fiber (React 16+) is the reimplementation of React's reconciliation algorithm. It enables incremental rendering (splitting work into chunks), prioritization of updates (user input over data fetching), and is the foundation for features like Suspense and Concurrent Mode.

4. Why should you use functional updates with useState?

setCount(prev => prev + 1) guarantees you're reading the latest state value. Without it, closures may capture stale state: setCount(count + 1) called multiple times in an event handler would only increment once because all calls see the same count.

5. When should you use useReducer instead of useState?

useReducer shines when: state has many sub-values that update together, transitions follow complex rules, you want testable state logic (pure reducer function), or you need to pass dispatch down instead of multiple setter callbacks.

6. What is the difference between useMemo and useCallback?

useMemo(() => computeValue(), [deps]) caches the return value. useCallback(fn, [deps]) caches the function itself. Technically, useCallback(fn, deps) is equivalent to useMemo(() => fn, deps). Both prevent unnecessary re-renders when passed as props to memoized children.

7. Why can't Error Boundaries be implemented as function components?

React has not yet introduced hook equivalents for the error boundary lifecycle methods (getDerivedStateFromError and componentDidCatch). This is one of the few remaining reasons to use class components. Libraries like react-error-boundary provide a wrapper for easier usage.

8. What does React.memo do?

React.memo is a higher-order component that performs a shallow comparison of props. If props are the same, it skips re-rendering and reuses the last rendered result. You can provide a custom comparison function for more control.

9. What problem does the Context API solve, and what is its limitation?

Context eliminates prop drilling by providing values to deeply nested components. However, when the context value changes, ALL consumers re-render, even if they only use part of the value. Mitigation: split contexts by update frequency, memoize the value object, or use state management libraries for frequently changing state.

10. In React 18, what does Automatic Batching mean?

Before React 18, batching only happened in React event handlers. In React 18, state updates are batched everywhere - inside promises, setTimeout, native event handlers, etc. This means fewer re-renders and better performance by default. Use flushSync() if you need to opt out.

Quiz Vue - 10 Questions

1. What is the main advantage of Vue 3's Composition API over the Options API?

The Composition API lets you organize code by logical concern (all user-related logic together) rather than by option type (all data together, all methods together). Composables enable clean logic extraction and reuse across components - similar to React's custom hooks.

2. What happens if you destructure a reactive() object in Vue 3?

Destructuring a reactive() object creates plain (non-reactive) variables. Use toRefs() to destructure while maintaining reactivity: const { name, email } = toRefs(state). This is a common gotcha in Vue 3.

3. What is the difference between watch and watchEffect in Vue 3?

watch takes explicit source(s) and a callback with old/new values - similar to watching specific variables. watchEffect runs immediately and auto-tracks any reactive dependency accessed inside it - similar to React's useEffect but with automatic dependency detection.

4. Why is Pinia recommended over Vuex for Vue 3?

Pinia removes the mutations layer (direct state changes), has first-class TypeScript support, is ~1.5KB (vs ~6KB for Vuex), uses flat stores instead of nested modules, and supports the Composition API setup syntax. It's the officially recommended state management for Vue 3.

5. When should you use v-show instead of v-if?

v-show uses CSS display:none (element always in DOM), so toggling is cheap. v-if adds/removes from DOM, which is more expensive for frequent toggles. Use v-if for conditions that rarely change (lazy rendering), v-show for frequent toggles (tabs, dropdowns).

6. What is hydration in the context of Vue SSR?

Hydration takes server-rendered HTML (which is static and non-interactive) and "hydrates" it by attaching Vue's reactivity system and event listeners on the client. The HTML is visible immediately (fast FCP), then becomes interactive after hydration completes.

7. What does <script setup> provide in Vue 3.2+?

<script setup> is a compile-time sugar for the Composition API. Variables, functions, and imports declared at the top level are automatically available in the template - no explicit return needed. It also enables better TypeScript inference and slightly better runtime performance.

8. What is the purpose of keep-alive in Vue?

<keep-alive> caches inactive component instances instead of destroying them. When the user switches back, the component's state (form data, scroll position, etc.) is preserved. Use include/exclude props to control which components are cached. Cached components get onActivated/onDeactivated lifecycle hooks.

9. How does Vue 3's reactivity system work under the hood?

Vue 3 uses JavaScript Proxy (replacing Vue 2's Object.defineProperty). Proxy can intercept ALL operations on an object (including property addition/deletion, which Vue 2 couldn't detect). ref() wraps the value in an object with getter/setter. This is why ref needs .value - the getter/setter triggers dependency tracking.

10. What is the difference between router.push() and router.replace()?

router.push() adds a new entry to the browser history stack - the user can press Back to return. router.replace() replaces the current history entry - the user can't go back. Use replace for redirects (e.g., after login, redirect to dashboard without login page in history).

class CachedProductRepository implements ProductRepository
{
    public function __construct(
        private EloquentProductRepository $repository,
        private int $ttl = 3600,
    ) {}

    public function findById(int $id): ?Product
    {
        return Cache::remember(
            "product:{$id}",
            $this->ttl,
            fn() => $this->repository->findById($id)
        );

        $product = $this->repository->update($id, $data);
        Cache::forget("product:{$id}");
        return $product;
    }

    public function delete(int $id): bool
    {
        $result = $this->repository->delete($id);
        Cache::forget("product:{$id}");
        return $result;
    }
}

Challenge 2: React - Custom Hook with Debounce React

Create a useSearchUsers custom hook that fetches users from /api/users?q=query with 300ms debounce, loading state, error handling, and request cancellation on unmount.

Hint: Use useState for users/loading/error, useEffect with setTimeout for debounce, AbortController for request cancellation. The cleanup function should clear the timeout AND abort the fetch. 
function useSearchUsers(query) {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState(null);

  useEffect(() => {
    if (!query.trim()) {
      setUsers([]);
      return;
    }

    const controller = new AbortController();
    setLoading(true);
    setError(null);

    const timer = setTimeout(async () => {
      try {
        const res = await fetch(
          `/api/users?q=${encodeURIComponent(query)}`,
          { signal: controller.signal }
        );
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        const data = await res.json();
        setUsers(data);
      } catch (err) {
        if (err.name !== 'AbortError') {
          setError(err.message);
        }
      } finally {
        setLoading(false);
      }
    }, 300);

    return () => {
      clearTimeout(timer);
      controller.abort();
    };
  }, [query]);

  return { users, loading, error };
}

Challenge 3: Vue - Composable with Pagination Vue

Create a usePagination composable that handles paginated API requests with reactive page state, loading, and methods to go to next/prev/specific page.

Hint: Use ref for page, data, totalPages, loading. Use watch on page to trigger fetchFn. Return navigation methods (next, prev, goTo) that update the page ref. The watcher handles the actual fetching. 
import { ref, watch } from 'vue';

export function usePagination(fetchFn, perPage = 15) {
  const data = ref([]);
  const page = ref(1);
  const totalPages = ref(1);
  const loading = ref(false);
  const error = ref(null);

  async function load() {
    loading.value = true;
    error.value = null;
    try {
      const result = await fetchFn(page.value, perPage);
      data.value = result.data;
      totalPages.value = result.last_page;
    } catch (err) {
      error.value = err.message;
    } finally {
      loading.value = false;
    }
  }

  watch(page, load, { immediate: true });

  function next() {
    if (page.value < totalPages.value) page.value++;
  }

  function prev() {
    if (page.value > 1) page.value--;
  }

  function goTo(p) {
    if (p >= 1 && p <= totalPages.value) page.value = p;
  }

  return { data, page, totalPages, loading, error, next, prev, goTo, refresh: load };
}

Challenge 4: Laravel - Middleware Rate Limiter Laravel

Create a custom middleware that rate-limits API endpoints to 60 requests per minute per user (authenticated) or per IP (guest). Return appropriate headers (X-RateLimit-Limit, X-RateLimit-Remaining, Retry-After).

Hint: Use Laravel's RateLimiter facade. Generate a unique key from user ID or IP. Use RateLimiter::tooManyAttempts() to check, RateLimiter::hit() to increment, and RateLimiter::availableIn() for Retry-After. 
class ApiRateLimiter
{
    public function handle(Request $request, Closure $next, int $maxAttempts = 60)
    {
        $key = $this->resolveKey($request);

        if (RateLimiter::tooManyAttempts($key, $maxAttempts)) {
            $retryAfter = RateLimiter::availableIn($key);

            return response()->json([
                'message' => 'Too many requests.',
                'retry_after' => $retryAfter,
            ], 429)->withHeaders([
                'Retry-After' => $retryAfter,
                'X-RateLimit-Limit' => $maxAttempts,
                'X-RateLimit-Remaining' => 0,
            ]);
        }

        RateLimiter::hit($key, 60); // Decay in 60 seconds

        $response = $next($request);

        return $response->withHeaders([
            'X-RateLimit-Limit' => $maxAttempts,
            'X-RateLimit-Remaining' => RateLimiter::remaining($key, $maxAttempts),
        ]);
    }

    private function resolveKey(Request $request): string
    {
        return $request->user()
            ? 'api:user:' . $request->user()->id
            : 'api:ip:' . $request->ip();
    }
}

1. Explain how Laravel's Service Container works and why it matters.

Senior Answer: "The Service Container is Laravel's implementation of an IoC (Inversion of Control) container. It's essentially a registry that knows how to create objects and their dependencies. When you type-hint an interface in a controller constructor, the container automatically resolves the correct implementation and injects it.

Why it matters: It decouples your code from specific implementations. I can bind PaymentGateway::class to StripeGateway in production and FakeGateway in tests - the controller code never changes. This makes testing trivial and swapping implementations painless.

In practice, I use it for: binding interfaces to implementations, creating singletons for expensive objects (like API clients), contextual binding when different classes need different implementations of the same interface, and scoped bindings for request-lifecycle objects in Laravel Octane."

2. You have a Laravel API endpoint that's responding slowly (3+ seconds). How do you diagnose and fix it?

Senior Answer: "First, I'd identify WHERE the bottleneck is, not guess:

  1. Laravel Telescope/Debugbar - Check query count and time. N+1 queries are the #1 culprit. If I see 200 queries, that's my answer.
  2. If it's queries: Add eager loading (with()), add database indexes, use select() to limit columns, consider query caching with Redis.
  3. If it's external API calls: Move to a queued job. The user gets an immediate response, and the API call happens in the background.
  4. If it's computation: Cache the result with Cache::remember(), or compute it in a scheduled job and cache the result.
  5. If it's serialization: Large collections being transformed through API Resources can be slow. Use cursor pagination or limit fields.

I always profile before optimizing. I've seen teams add Redis caching to an endpoint when the actual problem was a missing database index."

3. Explain the difference between React's useMemo, useCallback, and React.memo. When would you use each?

Senior Answer: "They're all memoization tools but at different levels:

  • useMemo - Memoizes a computed VALUE. Use it when you have an expensive calculation that shouldn't re-run on every render. Like sorting a 10K item list - you only want to re-sort when the list or sort criteria changes.
  • useCallback - Memoizes a FUNCTION reference. Use it when passing callbacks to memoized children - without it, a new function reference is created every render, defeating React.memo on the child.
  • React.memo - Memoizes a COMPONENT. It does a shallow prop comparison and skips re-rendering if props haven't changed.

The key insight: these only matter when they prevent actual re-renders. I see developers wrap everything in useMemo/useCallback - that's premature optimization that adds complexity without benefit. I use them when profiling shows a performance problem, or when passing to a React.memo child. The React DevTools profiler is my first step."

4. How would you design the authentication system for a React SPA + Laravel API?

Senior Answer: "It depends on the deployment topology:

Same domain (SPA + API): I'd use Laravel Sanctum's SPA authentication. The flow is: SPA calls /sanctum/csrf-cookie to get an XSRF token, then sends login credentials. Laravel sets an httpOnly session cookie. All subsequent requests include the cookie automatically. No token management in the frontend. This is the most secure approach because tokens aren't stored in localStorage (XSS-vulnerable).

Different domains / Mobile: I'd use Sanctum token authentication. After login, generate a personal access token, return it to the client, store it in memory (not localStorage). Send it as a Bearer token in the Authorization header. Implement token rotation - issue a new token periodically and revoke old ones.

In both cases: use HTTPS only, implement rate limiting on auth endpoints, add 2FA for sensitive accounts, and use Laravel's built-in password hashing (bcrypt/argon2). I'd never roll my own auth - the attack surface is too large."

5. What's the difference between Vue's ref() and reactive()? When do you use each?

Senior Answer: "ref() wraps any value in a reactive object with a .value property. reactive() makes an object itself reactive using JavaScript Proxy.

I generally prefer ref() for several reasons:

  1. It works consistently with both primitives and objects
  2. You can destructure and pass refs around without losing reactivity
  3. The explicit .value makes it clear in code that you're dealing with reactive data
  4. reactive() has a gotcha - destructuring loses reactivity unless you use toRefs()

I use reactive() when I have a group of related values I'll always access together - like a form state object where I never need to pass individual fields around. But if there's any chance I'll need to destructure or pass individual values, I use ref()."

6. Tell me about a time you had to make a difficult architectural decision. What trade-offs did you consider?

Framework for answering: This is a behavioral question. Use the STAR method (Situation, Task, Action, Result) and focus on trade-offs.

Example: "We had a growing Laravel monolith serving 500K daily requests. The team debated microservices. I advocated for the 'modular monolith' approach instead - extracting code into well-defined modules with clear interfaces, but keeping them in one deployable.

Trade-offs I considered:

  • Microservices would give us independent deployment but add massive operational complexity (service mesh, distributed tracing, eventual consistency) - we had 4 developers, not 40
  • The modular monolith gave us 80% of the boundary benefits with 20% of the complexity
  • We could extract a module into a service later IF it actually needed independent scaling

Result: Faster development velocity, clearer code boundaries, and when we eventually did extract the notification service (it had different scaling needs), the clean interfaces made it straightforward."

7. How do you handle database migrations in a zero-downtime deployment?

Senior Answer: "The key principle is: never make a breaking schema change in a single deployment.

For adding a column: Add it as nullable first, deploy new code that writes to it, backfill existing rows in batches, then add the NOT NULL constraint in a separate migration.

For removing a column: Stop reading from it in code first, deploy. Then remove it in a subsequent migration.

For renaming: Create the new column, deploy code that writes to both, backfill, deploy code that reads from new column, then drop old column.

For large table alterations (millions of rows): Use pt-online-schema-change or gh-ost which create a shadow table, copy data in chunks, then do an atomic rename. Never ALTER TABLE directly on a hot table.

I also always ensure migrations are idempotent and reversible. The down() method should actually work."

8. Explain the concept of React Server Components and how they differ from SSR.

Senior Answer: "Traditional SSR renders the entire component tree to HTML on the server, sends it to the client, then hydrates everything (making it interactive). The full JS bundle is still sent.

React Server Components (RSC) are fundamentally different: they run ONLY on the server and send their rendered output (not their code) to the client. The JS for Server Components is never shipped to the browser.

Key differences:

  • SSR: Server renders to HTML, client re-renders and hydrates. All component code is in the bundle.
  • RSC: Server Components stay on the server. Only Client Components (marked with 'use client') are in the bundle.
  • RSC can directly access databases, file systems, and server-only APIs without an API layer
  • They're composable with Client Components - you can pass Server Component output as children to Client Components

The practical benefit: dramatically smaller client bundles. A data table component that fetches from a DB and renders 10K rows? Zero KB of client JS if it's a Server Component."

9. How do you ensure code quality in a team setting?

Senior Answer: "I believe in automation over convention. My approach:

  1. Automated standards: ESLint/Prettier for JS, PHP-CS-Fixer/Pint for PHP, configured in CI. No debates about formatting.
  2. Static analysis: PHPStan/Larastan at level 6+ for PHP, TypeScript strict mode for frontend. Catches bugs before runtime.
  3. Testing pipeline: Unit tests for business logic, integration tests for API endpoints, E2E tests for critical user flows. CI blocks merge if tests fail.
  4. Code review: I review for architecture and logic, not style (that's automated). I look for: does this solve the right problem? Is it maintainable? Are there edge cases?
  5. PR standards: Small, focused PRs with descriptions. One PR = one concern. Large PRs get stale and get rubber-stamped.

The goal is to make quality the path of least resistance, not something that requires discipline."

10. What's the biggest mistake you've made as a developer, and what did you learn?

Tips for answering:

  • Choose a real mistake, not a humble-brag ("I work too hard")
  • Show accountability - don't blame others
  • Focus 70% on what you learned and changed, 30% on the mistake
  • Show how you prevented it from happening again (process change, not just "I'll be more careful")

Example: "I once deployed a database migration to production that added a NOT NULL column to a 20M row table without a default. It locked the table for 8 minutes during peak traffic. I learned to always: test migrations against production-size data, use the expand/contract migration pattern, and have a rollback plan before deploying any migration. I wrote a team runbook for safe migrations that we still use."
